HarborSQL

Most data-platform requests are not big-data jobs. Run an in-memory SQL endpoint for supported Unity Catalog Delta reads, offload the many small queries that fit on a single server, and stop paying a Spark premium for them.

Where it fits

Offload the requests that never needed Spark.

Data platforms still need Spark for large scans, joins, ETL, and distributed compute. But a large share of application, API, notebook, and operational SQL is small enough to execute in memory on one server. HarborSQL gives those reads a cheaper path while keeping Unity Catalog as the control plane.

Keep Unity Catalog in charge

HarborSQL checks access through Unity Catalog and uses short-lived table credentials for the caller.

Use an in-memory SQL engine

HarborSQL opens Unity Catalog-managed Delta tables with delta-rs and executes supported SELECT queries with DataFusion on your own compute.

One line change in the code

Keep your code using the Databricks SQL connector and route supported queries to HarborSQL instead of a Databricks endpoint.

Keep Spark for big jobs

HarborSQL is not a full warehouse clone. Use it for read-only queries that fit the current support matrix, and leave distributed work on Spark.

How it works

Keep the client shape. Move small-query execution onto your compute.

HarborSQL accepts Databricks SQL connector-style requests, resolves Unity Catalog Delta tables as the caller, opens the data with delta-rs, executes read-only SQL in memory with DataFusion, and returns Databricks-compatible result sets.

Security model

Authorization stays where your governance already lives.

Unity Catalog remains the authority

HarborSQL forwards the caller bearer token to Unity Catalog and asks for temporary table credentials only for tables the caller can access.

No persistent token storage

Databricks bearer tokens and temporary cloud credentials are not persisted. Cached table providers are keyed by a process-local HMAC of the caller token.

Read-only by design

The current server targets read-only SELECT workloads, result limits, session limits, operation TTLs, and request body limits.

Client compatibility

From warehouse endpoint to HarborSQL endpoint.

Existing Python clients keep the Databricks SQL connector. Put HarborSQL behind HTTPS, change the server hostname, and send the small read path to the in-memory engine.

One line change 
from databricks import sql
import os

SERVER_HOSTNAME="sql.harborsql.com"

connection = sql.connect(
    server_hostname=SERVER_HOSTNAME,
    http_path="/sql/1.0/warehouses/local",
    access_token=os.environ["DATABRICKS_TOKEN"],
    catalog="workspace",
    schema="analytics",
)

Local server

Run it beside the services generating the small queries.

Release publishing produces a Linux x86_64 Docker image, Linux binary archive, and macOS Apple Silicon archive when enabled. The same server path works for local development, EC2 benchmarks, and private deployments behind TLS where the goal is to serve memory-sized reads without starting Spark compute.
